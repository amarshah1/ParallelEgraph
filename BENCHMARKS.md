# Benchmarks

Three benchmark sources in this repo. They measure different things and come from different places.

## 1. SMT-LIB benchmarks (`synthetic_benchmarks/`)

End-to-end solver benchmarks. Each `.smt2` file is a complete QF_UF problem with a known UNSAT answer that the solver must derive via congruence closure. Drive them with the CLI binary (`cpp/build/parallel-egraph` or `target/release/parallel-egraph`), or sweep a folder with [`bench.py`](bench.py).

Generated by [`gen_bench.py`](gen_bench.py) — four problem families, each parameterized by a single integer `n`. Every benchmark ends with one disequality whose negation is implied by the asserted equalities, so the answer is always UNSAT and the solver must process the entire formula to derive it.

### Families

| family | merges | congruences | shape                                                                            |
|--------|--------|-------------|----------------------------------------------------------------------------------|
| chain  | 2n+1   | n           | `a_{i+1}=f(a_i)`, `b_{i+1}=f(b_i)`, then `a_0=b_0` ⇒ `a_n=b_n` (sequential)      |
| grid   | n      | n²          | `a_i=b_i` ⇒ `f(a_i,a_j)=f(b_i,b_j)` for all `i,j` (binary `f`)                   |
| cube   | n      | n³          | `a_i=b_i` ⇒ `f(a_i,a_j,a_k)=f(b_i,b_j,b_k)` for all `i,j,k` (ternary `f`)         |
| exp    | 1      | 2^(n+1)−2   | one merge `a=b` cascades through `n` layers of 2 unary functions each            |

For grid/cube, the disequality compares the two giant sets of f-terms via a **balanced binary `g`-tree** ([`nest_balanced`](gen_bench.py:25-41)) so disequality depth is O(log m) where m is the number of f-terms — depth doesn't blow up.

For exp, each layer's terms are introduced via named constants (`ta1_0`, `ta1_1`, …) and equalities, because the cascade requires referencing the previous layer's intermediates by name. The cascade depth is exactly `n` rounds of congruence closure.

### Files in `synthetic_benchmarks/`

The directory currently has:
- `chain_n*` — *(currently absent — regenerate via `gen_bench.py sweep:chain ...`)*
- `cube_n5_unsat.smt2` … `cube_n80_unsat.smt2` (step 5)
- `exp_n1_unsat.smt2` … `exp_n17_unsat.smt2` (step 2; ≥18 is huge — `exp_n17` already has 262K congruences)
- `grid_n5_unsat.smt2` … `grid_n80_unsat.smt2` (step 5)

### Regenerating

```bash
# single benchmark to stdout
python gen_bench.py grid 20

# write a single benchmark to ./synthetic_benchmarks
python gen_bench.py grid 20 synthetic_benchmarks

# all four families at one size
python gen_bench.py all 30 synthetic_benchmarks

# sweep one family
python gen_bench.py sweep:cube 5 80 5 synthetic_benchmarks

# sweep all families
python gen_bench.py sweep 5 30 5 synthetic_benchmarks
```

### Running

```bash
# single problem
PARLAY_NUM_THREADS=8 cpp/build/parallel-egraph synthetic_benchmarks/exp_n11_unsat.smt2 --timing --parallel

# whole folder
python bench.py synthetic_benchmarks --parallel
```

### What's measured

`solve_timed` reports per-phase timings to stderr: `parse build merge rebuild check solve total`. The interesting parallel phase is **rebuild** (congruence closure). `parse` time is dominated by yaspar/recursive-descent SMT-LIB parsing for the giant disequality, especially on cube/grid at large n — it can dwarf solve time and is not what you're benchmarking.

## 2. SMT-COMP QF_UF benchmarks (`benchmarks/`)

Real-world QF_UF problems pulled from the SMT-LIB benchmark library / SMT-COMP submissions. Unlike `synthetic_benchmarks/`, these were not generated by us — they have anonymized symbol names (`x117`, `x446`, …) and the expected `sat`/`unsat` answer is **not** encoded in the filename. To validate, diff against z3/cvc5 output.

Subdirectories and counts:

| folder                     | files | source                                                                |
|----------------------------|-------|-----------------------------------------------------------------------|
| `2018-Goel-hwbench/`       | 302   | hardware verification (Goel, 2018)                                    |
| `QG-classification/`       | 3094  | quasigroup classification (large; the bulk of the suite)              |
| `eq/`                      | 41    | equality-heavy                                                        |
| `NEQ/`                     | 25    | disequality-heavy                                                     |
| `PEQ/`, `SEQ/`             | 19+14 | misc QF_UF                                                            |
| `20170829-Rodin/`          | 7     | Rodin proof obligations                                               |
| `20190906-CLEARSY/`        | 19    | CLEARSY industrial submissions                                        |

Use these for correctness regression and for measuring solve time on workloads we did not design. Most are small/quick; `QG-classification/` has long-tail outliers.

### Running

```bash
# single file (no expected-answer assertion)
PARLAY_NUM_THREADS=8 cpp/build/parallel-egraph benchmarks/2018-Goel-hwbench/QF_UF_pgm_protocol.1.prop6_ab_cti_max.smt2 --timing --parallel

# whole folder via bench.py — note that bench.py expects the filename to encode
# the expected result for synthetic benchmarks; for SMT-COMP files, just compare
# stdout against z3 manually
python bench.py benchmarks/2018-Goel-hwbench --parallel --csv goel.csv

# diff our output against z3
for f in benchmarks/2018-Goel-hwbench/*.smt2; do
  ours=$(cpp/build/parallel-egraph "$f" --parallel 2>/dev/null)
  z3=$(z3 "$f" 2>/dev/null | head -1)
  [ "$ours" != "$z3" ] && echo "DIFF $f: ours=$ours z3=$z3"
done
```

## 3. In-process synthetic workloads (`rebuild_compare`)

Pure closure-phase microbenchmarks. No SMT parsing, no file I/O — workloads are built in memory and only the closure call is timed.

Two parallel implementations of the same workload generator:

- Rust: [`benches/rebuild_compare.rs`](benches/rebuild_compare.rs) — run via `cargo bench --bench rebuild_compare`
- C++: [`cpp/bench/rebuild_compare.cpp`](cpp/bench/rebuild_compare.cpp) — built as `cpp/build/rebuild_compare_bench`

Both versions use the identical workload table:

| name    | leaves | n_fns | nodes     | merges  | depth |
|---------|--------|-------|-----------|---------|-------|
| small   | 1,000  | 4     | 10,000    | 2,000   | 1     |
| medium  | 10,000 | 8     | 200,000   | 20,000  | 1     |
| large   | 50,000 | 16    | 1,000,000 | 100,000 | 1     |
| deep-s  | 1,000  | 4     | 10,000    | 2,000   | 3     |
| deep-m  | 10,000 | 8     | 200,000   | 20,000  | 3     |
| deep-l  | 50,000 | 16    | 1,000,000 | 100,000 | 3     |

### Workload generator

Per-workload construction (deterministic; seed is `0xC0FFEE ^ n_nodes`):

1. `n_leaves` `x`-leaves and `n_leaves` `y`-leaves are added.
2. Function nodes are built in `depth` levels. Each level contains roughly `n_nodes / depth` arity-2 nodes whose two children are sampled uniformly from the **previous** level (level 0 = all leaves). Op names are drawn from a pool of `n_fns` distinct names per level (`f{lvl}_{k}`).
3. `n_merges/2` random `(x_i, x_j)` and `n_merges/2` random `(y_i, y_j)` equalities are sampled. They are returned as a `Vec<(Id, Id)>` separately from the e-graph.

`depth=1` is a flat DAG (functions only over leaves). `depth=3` produces multi-round cascades — closure can't finish in one round because parents at level k+1 only become merge candidates after their level-k children get merged.

The Rust and C++ generators use different RNGs (`SmallRng` vs `mt19937_64`), so the *exact* DAGs differ between languages, but the shape parameters and within-language determinism are preserved.

### What's measured

11 timed trials + 3 warmup. **The e-graph build and the equality-list construction happen outside the timed region** — only the close call is timed. Each trial rebuilds from scratch (no state carries between trials).

- `nelson_seq` median ms: `EGraph::sequential_close_nelson(&equalities)` — classic sequential Nelson-style worklist closure, used as the baseline.
- `par_close` median ms: `EGraph::parallel_close(&equalities)` — the parallel BSP closure.
- `par_spd` = `nelson_seq / par_close` — speedup of parallel over the sequential baseline.

Note: `parallel_close` includes the initial unions, the BSP rebuild loop, and union-find work — not just `parallel_rebuild`. To isolate rebuild, you'd need to call `parallel_merge_all` outside the timed region.

### Running

```bash
# Rust
cargo bench --bench rebuild_compare

# C++
PARLAY_NUM_THREADS=8 cpp/build/rebuild_compare_bench

# Sweep thread counts
for T in 1 2 4 8 12; do
  PARLAY_NUM_THREADS=$T cpp/build/rebuild_compare_bench 2>/dev/null \
    | grep -E '^large|^deep-l' | sed "s/^/T=$T  /"
done
```

The Rust version uses `rayon::current_num_threads()` (set via `RAYON_NUM_THREADS`); the C++ version uses parlay's scheduler (set via `PARLAY_NUM_THREADS`).
